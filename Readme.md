# Решение тестового задания - cron-задание для ALD Pro

Здравствуйте! Это моё решение задачи по созданию cron-задания. Сделал два варианта - bash-скрипт и Salt State, чтобы показать разные подходы.

## Что делает решение

Оба варианта делают одно и то же:
- Создают файл `/etc/cron.d/test_cron`
- Настраивают задание, которое запускается каждые 5 минут
- При каждом запуске записывают текущее время в файл `/tmp/runtime.txt`

## Как запустить

### Bash-скрипт

Перейдите в папку с решением и выполните:

```bash
chmod +x bash/create_cron.sh
sudo bash/create_cron.sh
```

### Salt State
Файл salt/create_cron.sls написан для использования в инфраструктуре SaltStack, которую использует ALD Pro.  
Если у вас настроен salt-master, просто скопируйте файл в /srv/salt/states/ и примените:

```bash
sudo salt 'target-minion' state.apply test_cron
```

Для локального тестирования (если установлен salt-minion):
```bash
sudo salt-call --local state.apply salt/test_cron.sls
```

### Почему два варианта?
Bash-скрипт - это просто и понятно. Запустил один раз, и готово. Подходит для быстрого развёртывания на одной машине или для тестирования.

Salt State - это уже уровень инфраструктуры. Файл описывает желаемое состояние системы, а Salt сам разбирается, как его достичь. Такой подход масштабируется на сотни серверов и гарантирует, что конфигурация не «уплывёт» со временем.
Кстати, в SLS я использовал file.managed вместо cron.present. Потому что file.managed даёт полный контроль над содержимым файла - вижу всё явно, могу добавить комментарии, переменные окружения. С cron.present больше абстракции, а мне хотелось прозрачности.
Как устроено

**Bash-скрипт**

    Проверяет, что запущен от root (без sudo не сработает)
    Создаёт cron-файл с правильными правами (644, root:root)
    Использует heredoc для генерации содержимого
    Экранирует $(date) как \$\(date\), чтобы команда выполнялась при запуске cron, а не при создании файла
    Проверяет результат после создания

**Salt State**

    Использует state file.managed для полного контроля над файлом
    Указывает обязательные права и владельца
    Добавляет state для проверки, что cron-демон запущен


Немного о безопасности

Оба решения учитывают важные моменты:

    Файлы в /etc/cron.d/ должны иметь права 644 и принадлежать root — иначе cron их проигнорирует
    В cron-файле явно указан SHELL и PATH для переносимости
    Ошибки перенаправлены в stdout (2>&1), чтобы ничего не терялось
    Скрипты идемпотентны т.е. можно запускать сколько угодно раз, результат будет одинаковым

Что было интересного

Самый коварный момент - с экранированием. В bash-скрипте внутри heredoc нужно было написать 
```bash
\$\(date\)
```
чтобы при создании файла записалась именно строка $(date), а не текущее время. Иначе cron выполнял бы команду один раз при создании файла, а не при каждом запуске.
Ещё интересный момент - в /etc/cron.d/ формат отличается от пользовательского crontab: там нужно указывать пользователя (шестое поле). Сначала я об этом забыл, но потом разобрался.

Если что-то пойдёт не так

    Проверьте, что запускаете от root (или через sudo)
    Посмотрите логи cron: grep CRON /var/log/syslog (для Debian/Ubuntu) или grep CRON /var/log/cron (для RHEL/ALD Pro)
    Убедитесь, что cron-демон запущен: systemctl status cron
